模型越来越能独立完成任务以后，计划模式会变得有些尴尬。我们把工作交给 AI，希望少操心，它却先交来一份方案，等我们读完、修改、批准，才开始干活。

这一步还值不值得保留？我的判断是，计划模式仍然有用，但它应该更少出现。能力进步理应让模型接过更多工作，包括自己决定怎样规划。需要人参与的地方，应当有一个值得人作出的决定。

## 一、模型越强，越没必要让人盯着步骤

![](../../assets/planning-mode/01-autonomous-planning.png)

先分清两个动作。模型为完成任务安排步骤，和模型停下来让用户批准步骤，是两回事。直接执行的 AI 也可以先查资料、比较做法，再根据结果调整顺序。没有打开计划模式，不能据此判断它有没有规划。

Claude Code 的[官方最佳实践](https://code.claude.com/docs/en/best-practices)就给了一个很具体的建议。修正错字、添加一行日志、重命名变量这类范围清楚的小改动，可以直接做，计划本身也会增加开销。同一份文档建议，对需要规划的工作，先读懂相关代码，再拟方案。

这两条放在一起，意思很清楚。规划需要多少，要跟着任务走。

如果模型已经能可靠地找出涉及的文件，知道改完该怎么检查，还要求用户逐项确认这些常规步骤，就把一部分工作重新交回了用户。懂技术的人要花时间阅读，不懂的人也很难判断，最后可能只剩下一句“可以，继续”。

即使任务很大，也未必需要这样做。目标、约束和验收要求已经明确，改动又能在独立副本里验证，模型完全可以自行拆解任务。用户需要看的是结果是否符合要求。步骤多，只能说明模型需要认真组织工作，不能单独证明用户必须参与组织。

## 二、能力再强，也要知道我们愿意接受什么

![](../../assets/planning-mode/02-decision-tradeoffs.png)

计划模式更有价值的场合，是同一个要求可以通向几种不同的结果。

拿一个假设任务来说，让 AI 降低网站运行成本。它可能找到更便宜的服务，也可能建议减少备份、缩短日志保留时间。这些做法都可能省钱，却会改变出故障后能恢复到什么程度，以及以后还能查到多少记录。

模型可以分析或估算代价，可以根据已有要求提出建议。用户尚未表达过的取舍，仍然需要补充。它越能干，越有可能把一个方向完整地执行下去，这就更需要在动手前弄清楚方向是否被接受。

这里有用的计划，应当把选择讲明白。推荐采用哪种做法，为什么，用户会因此放弃什么。列出十几个操作步骤，对这个决定未必有帮助。这种讨论也可以发生在执行过程中，不必每次都专门切换模式。

Claude Code 的官方指南也建议，在开发较大功能前，让模型就交互体验和边界情况等问题询问用户，再形成规格说明。讨论能帮用户发现自己还没想过的要求，模型也有机会把含糊的想法变成能检查的目标。

不过，已经说清的偏好就应该继续生效。用户明确要求保留备份，模型应当在这个条件下找办法。每次都把同一个选择拿回来问，会让确认变成负担。

## 三、计划写得再完整，也有它解决不了的问题

![](../../assets/planning-mode/03-prototype-verification.png)

并非所有不确定性都适合靠讨论消除。

界面是否顺手、文章语气是否合适，有时要看到实际结果才知道。低成本做出一个可修改的版本，能让用户给出具体反馈。要求用户先批准一份详尽方案，可能只是逼他提前回答尚且回答不了的问题。

Claude Code 的文档介绍过用检查点恢复代码和对话的方式，也提醒它不能覆盖 Bash 命令或外部进程造成的所有变化。这个限制很重要。先试一试的前提，是确实知道哪些后果可以撤回。

计划还会受新信息影响。模型读过代码，才发现原来的接口用不了；跑过测试，才知道某条路径有问题。此时应该允许它调整做法。把早期计划固定得过细，反而容易让后续工作围着旧假设打转。

用户读完计划，也没有替执行结果作出保证。一份写得流畅的方案，照样可能漏掉条件。官方指南把测试、构建检查和界面截图放在显著位置，要求模型提供能核对的结果。批准方案以后，这些验证仍然要做。

因此，评价计划模式不能只看方案有多完整。还要看它有没有提前发现值得处理的问题，以及为此增加了多少阅读、等待和修改。

## 四、保留一个主动停下来的入口

![](../../assets/planning-mode/04-pause-control.png)

我更倾向于让普通任务默认向前推进。模型先完成必要的调查，在已有授权和约束内处理可逆的工作，遇到会明显改变目标、代价或影响范围的选择，再把问题交给用户。

作为一种交互设计，我仍然愿意保留完整的计划模式。有时用户当前只想讨论可行性，有时方案要交给团队审阅，实施还得等预算或人员安排。此时一份能独立阅读、能交接的计划，本身就是需要交付的东西。

还有一种很实际的需要。用户不熟悉手头项目，也无法预判 AI 会改到哪里，就希望明确告诉它，先调查和解释，暂时不要实施。只要这种需要存在，主动进入计划模式的入口就有价值。

模型能否可靠判断何时该停，目前仍需要在具体工具和任务里验证。这个判断还不够可靠时，用户手动打开计划模式，是一种合理的控制方式。

如果将来模型能把这件事做得更好，我希望看到的是，常规工作直接完成，关键选择及时说明。用户不再需要在任务开始前，就猜准这一次到底该不该按下“计划模式”。
